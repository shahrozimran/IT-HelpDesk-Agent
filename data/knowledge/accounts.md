# Account access and password recovery

SYNTHETIC TRAINING DOCUMENT. Version 2026-11-01. This educational guide does not provide a live recovery link and does not authorize the agent to reset any real account.

## Identify the access problem
Ask whether the user forgot the password, sees an account-lockout message, cannot receive their second factor, or can sign in but lacks permission to a specific application. The error category determines the next step. Check the simulated accounts service when multiple users report failure. A general outage can resemble an individual authentication problem.

For a suspected typo, ask the user to check keyboard layout, Caps Lock and the entered username privately. Never ask them to send a password to the assistant. Avoid repeated attempts: in this fictional system, five failed sign-ins within ten minutes trigger a temporary fifteen-minute lockout. The assistant cannot measure the user's actual counter or unlock the account. Clearly label these numbers as synthetic policy.

## Password recovery and multi-factor issues
For a forgotten password, direct the user to the recovery portal identified by their actual institution through its trusted website or administrator. Do not invent a portal URL. The user completes identity verification themselves. The agent cannot validate identity, set a password, read an authentication code or bypass verification.

During the simulated temporary lockout, wait fifteen minutes after the most recent failed sign-in before trying again, unless an authorized technician supplies other guidance. If the issue persists, ask the authorized helpdesk for identity-verified assistance. If the user has lost access to their second factor, an authorized support process is required; do not recommend disabling multi-factor protection. The assistant should state that its simulated ticket system does not perform real account recovery.

## Privacy and escalation
If a user suspects an account compromise, advise contacting their institution's authorized support channel promptly and following its verified recovery procedure. Do not collect sensitive identity documents in this chat. Record only non-secret details such as the error category, affected application, approximate time and completed checks.

A saved preference may include the device operating system or the user's preferred explanation style. Passwords, one-time codes, recovery secrets, API keys and unnecessary personal details must never be stored in long-term memory. Obtain user permission before saving an incident summary. Prepare an account-category simulated ticket only when requested, and require a separate explicit confirmation before creating it.
